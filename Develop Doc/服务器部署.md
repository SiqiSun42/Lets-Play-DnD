# 服务器端部署（迁移后：DSH 路径）

> 本文写给**在服务器上动手的人**（我这边只出步骤，不碰服务器）。
> 每一步都带验收命令；哪一步不对就停在那一堆，别往下走。
>
> 全文假设：项目在 `~/Lets-Play-DnD`，运行用户是 `siqisun`，代码从 GitHub `git pull` 更新。

## 0. 这次部署比上次多了什么

| 新增 | 为什么要 |
|---|---|
| **Node + dsh CLI** | 每个用户一个 DSH 实例（`Relay/instances.py` 按需拉起），实例是 `dsh web` 进程 |
| **`letsplaydnd` profile + 插件** | 实例的工具面（`read/write/edit/list_dir/skill` + 两个 MCP 工具）由 profile 决定 |
| **`.env` 里几个 `DSH_*` 变量** | 告诉 Flask：dsh 在哪、profile 从哪取、部署 patch 在哪 |
| **每用户 DSH_HOME / 快照库目录** | 每用户的模型 key 与存档快照都写在这里（都已 gitignore） |

旧流程（`System/`、`Prompts/`、`Tools/`）**不再推送到服务器**，所以服务器上不能回退旧路径。

> **冷启动与内存的优化**（预热、空闲回收、等待提示、缩短启动）单独记在
> [`实例优化方向.md`](./实例优化方向.md)——那是测试通过之后的事，部署时不用管。

## 1. 先处理服务器上的本地提交 ⚠️ 别跳过

服务器当前在 `00cbb7f prompt small change`，而 GitHub 上是 `00a86fa develop doc`——
**服务器有一条 origin 上没有的提交**。直接 `git pull` 可能冲突或把那条提交带歪。

```bash
ssh azure-dnd
cd ~/Lets-Play-DnD
git log --oneline -3          # 看清 00cbb7f 是什么
git show --stat 00cbb7f       # 改了哪些文件
git status                    # 有没有未提交的改动
```

然后二选一：

- **那条提交没用了** → `git checkout -- . && git reset --hard origin/main`（⚠️ 会丢弃本地改动）
- **要保留** → `git push origin HEAD:main`（或先 `git stash`），再往下走

```bash
# 验收：本地与远端一致
git fetch origin && git status -sb
```

> ⚠️ **两条顺序上的坑**：
> 1. `git pull` 本身**无害**（正在跑的旧进程已经把模块载进来了），但**pull 之后不要重启**
>    Flask——新的 `server.py` 默认走 DSH，而那时 dsh 还没装（第 2~4 步）。第 6 步才重启。
> 2. 落后多少、会不会冲突，在**本地**就能判定：`git merge-base --is-ancestor <服务器的HEAD> HEAD`
>    返回 0 说明服务器的提交已在主历史里、pull 是快进。（本次实测：服务器
>    `00cbb7f` 是祖先，落后 10 个提交，pull 直接快进，无冲突。）

## 2. 装 Node / pnpm / dsh

本地能跑通的组合是 **Node v24.15.0 + pnpm 12.4.2 + dsh 0.1.5-rc.1**，
服务器现在是 Node 20、没有 dsh。用 nvm 装一份 24，**不要动系统 Node**（别的服务可能在用）：

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
source ~/.nvm/nvm.sh
nvm install 24 && nvm alias default 24
npm i -g pnpm@12
npm i -g @deepseek-ai/dsh@0.1.5-rc.1     # 与本地同版本，别漂
```

```bash
# 验收
node -v            # v24.x
pnpm -v            # 12.x
which dsh && dsh -V
ls -d ~/.nvm/versions/node/*/bin/dsh      # 记下这个绝对路径，第 4 步要用
```

> 若 `npm i -g @deepseek-ai/dsh@0.1.5-rc.1` 报找不到版本，先 `npm view @deepseek-ai/dsh versions`
> 挑一个与本地接近的，并**把版本号在这里和本地对齐**。

## 3. 创建 `letsplaydnd` profile 并装插件

**⚠️ 不要从本地拷 `~/.dsh/profiles/letsplaydnd`**：那份 `cordis.patch.yml` 里写死了
`/Users/siqisun/学习/...` 的路径。在服务器上重新建一份：

```bash
cd ~/Lets-Play-DnD
export DSH_HOME=~/.dsh

# 只创建、不启动
dsh --profile letsplaydnd --from-default-profile web --dump-config > /dev/null

dsh plugin --profile letsplaydnd add '@deepseek-ai/dsh-mcp-client@0.1.5-rc.2'
dsh plugin --profile letsplaydnd add 'dsh2server@github:23J1633/dsh2server'
dsh plugin --profile letsplaydnd add ./dsh/plugins/fs-readguard       # link: 指向仓库
dsh plugin --profile letsplaydnd add ./dsh/plugins/tool-list-dir      # link: 指向仓库
```

```bash
# 验收 1：组合里必须有 dsh2server 与 MCP 行
DSH_HOME=~/.dsh dsh --profile letsplaydnd --dump-config | grep -nE "dsh2server|mcp|fs-readguard|list-dir"
```

**验收 2**：`~/.dsh/profiles/letsplaydnd/package.json` 的 `dsh.profile.bundles`
必须含 `@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app`、**`dsh2server`**。
若 `plugin add` 没把 `dsh2server` 加进 `bundles`，手工补上（它和别的一样是在 profile 里的一层）。

**验收 3**：`~/.dsh/profiles/letsplaydnd/cordis.patch.yml` 应当是**空的**（模板生成的空 patch）。
**部署行（agent-presets / MCP / sandbox-policy）不在 profile 里**，而是第 4 步那个
`DSH_INSTANCE_PATCHES` 指过去的仓库文件——两边都放会撞 `duplicate loader entry id`（本地踩过）。

### 3.5 铺共享模块兜底槽（一次性，但**不能省**）

DSH 的 bundle（`@deepseek-ai/dsh-base` / `dsh-web-app`）和一部分依赖（如 `@deepseek-ai/dsh-scope`）
**不在 profile 自己的 `node_modules` 里**，而由 `~/.dsh/profiles/node_modules` 这个"符号链接场"提供
（本机实测 187 项）。它在**第一次真正启动某个 profile** 时由 DSH 自己铺好；只跑 `--dump-config`
（只组合、不启动）不会铺。

⚠️ **每个用户实例都依赖它，实例自己 heal 不了**：profile 的 `node_modules` 是符号链接到共享那份，
而 **Node 解析模块用的是真实路径**，往上找 `node_modules` 最终落在共享的 `~/.dsh/profiles/` 下。
缺了它会看到实例日志里一句 `Cannot find package '@deepseek-ai/dsh-scope'`。

```bash
cd ~          # ⚠️ 必须在**别的目录**跑：仓库根有 .env，里面有 DSH_*，DSH 会拒绝加载它
DSH_HOME=~/.dsh timeout 30 dsh --profile letsplaydnd --host 127.0.0.1 --port 0 --no-open > /tmp/dsh-heal.log 2>&1 || true
tail -3 /tmp/dsh-heal.log
ls ~/.dsh/profiles/node_modules | wc -l        # 期望：上百（本机 187）
```
看到 `dsh web: http://127.0.0.1:<端口>` 就是启动成功了（`timeout` 会替你收掉它）。

## 4. 目录 + `.env`

```bash
mkdir -p ~/Lets-Play-DnD/.dsh-users ~/Lets-Play-DnD/.snapshots
```

往 `~/Lets-Play-DnD/.env` **追加**（`.env` 已在 gitignore 里，不会进仓库）：

```ini
# ── DSH：每用户实例 ────────────────────────────────────────────
# dsh 的绝对路径（nohup 起的进程 PATH 里没有 nvm）
DSH_BIN=/home/siqisun/.nvm/versions/node/v24.15.0/bin/dsh
# profile 从哪取（部署这份已经装好插件）
DSH_PROFILE_SOURCE=/home/siqisun/.dsh/profiles
# 实例要叠的部署 patch：仓库里那份（含 agent-presets 根、MCP 行、sandbox-policy）
DSH_INSTANCE_PATCHES=/home/siqisun/Lets-Play-DnD/dsh/profile.patch.yml
# 下面两个不写也行（默认就落在仓库里的 .dsh-users/ 与 .snapshots/）；
# 想按 FHS 放再打开，并且要确保 siqisun 可写：
# DSH_USERS_DIR=/var/lib/letsplaydnd/users
# DSH_SNAPSHOT_DIR=/var/lib/letsplaydnd/history
```

> 开关 `DSH_CONSULT_ENABLED` / `DSH_GAME_ENABLED` / `DSH_INSTANCE_AUTOSTART` **默认已开**，
> 不用写。要临时回退才写 `=0`（但服务器上没有旧流程文件，回退只在本机有意义）。

## 7. 端到端验收（浏览器里做）

第一条消息会触发**按需拉起该用户的 DSH 实例**，第一次大约 **10~40 秒**（之后复用）。
期间前端只是慢，不会报错；失败会在日志里看到 `[instances] 为用户 X 起实例失败：…`。

```bash
# 实例起来了
ls -la ~/Lets-Play-DnD/.dsh-users/
tail -20 ~/Lets-Play-DnD/.dsh-users/<用户名>/instance.log     # 末尾应有 dsh web: http://127.0.0.1:<随机端口>
cat ~/Lets-Play-DnD/.dsh-users/<用户名>/user.patch.yml        # provider 路由（应为该用户 settings.json 里的 provider）

# 回合结束后：快照有了
ls -la ~/Lets-Play-DnD/.snapshots/
```

浏览器侧逐项看：

- [ ] 游戏回合能出稿（思考 + 正文），单气泡
- [ ] 刷新页面，历史还在（`chat.db` 落库）
- [ ] 咨询也能用（走的是同一个实例、不同 skill）
- [ ] 面板（地点/背包/角色）显示正常
- [ ] 费用记在**该用户自己的 key** 上：故意用一个没配 key 的账号试——应当报"没有可用的模型 API Key"，而不是照常能玩

## 8. 回退与排障

| 症状 | 先看 |
|---|---|
| 发消息后一直"实例尚未连接" | `app.log` 里的 `[instances]` 行 + `.dsh-users/<用户名>/instance.log`；常见原因：`DSH_BIN` 路径不对、profile 没装好、`DSH2SERVER_ENDPOINT` 连不上 |
| `[instances] … 部署里没有模块兜底槽：~/.dsh/profiles/node_modules` | 见第 3.5 步：在 `cd ~` 下启动一次 profile 把它铺出来。**实例自己 heal 不了它**（Node 按真实路径解析，会走到共享的 `profiles/`） |
| 实例日志：`Cannot find package '@deepseek-ai/dsh-scope'` | 同上：兜底槽缺失 |
| **在仓库目录里手动跑 `dsh` 报** `… .env sets "DSH_BIN", which only the launching environment may set` | **DSH 拒绝从 `.env` 读 `DSH_*`**（`BOOTSTRAP_PREFIXES` 含 `"DSH_"`），而我们的 `.env` 里正好有那三个 `DSH_*`。手动调试请换到别的目录跑（`cd ~`），别在仓库根跑 `dsh`。（实例不受影响：它以 `cwd=<用户 home>` 启动，DSH 读的是那边不存在的 `.env`） |
| `duplicate loader entry id: mcp-letsplaydnd` | profile 的 `cordis.patch.yml` 里也放了部署行 → 清空它，只留 `DSH_INSTANCE_PATCHES` |
| `ERR_MODULE_NOT_FOUND` / 插件没生效 | 插件是 `link:` 到仓库的：确认 `~/.dsh/profiles/letsplaydnd/package.json` 的 `dependencies` 里有那三个，且路径指到**服务器上**的仓库 |
| 旧流程回退不了 | 预期：`System/`、`Prompts/`、`Tools/` 不再推送。要回退得 `git checkout <旧提交> -- System Prompts Tools` 且把开关设 0 |

## 9. 要知道的运行成本

- **每个活跃用户常驻一个 node 进程**（实例），加 MCP 服务一份。先上两三个用户，用
  `ps -o rss= -p <pid>` 看实例实际占用，再决定要不要做空闲回收（现在只有 `stop()` 手动停）。
- 实例的 web 端口是 `--port 0`（系统分配）、只监听 `127.0.0.1`，不占固定端口。
- 快照库在 `.snapshots/`，无变更的回合**不产生提交**（实测 71 ms / 0 增长）。
