## 2. 旧流程（现状）

5 个阶段，**由 Python 强制**：

```
0. 前置：软锁（团灭）检查；若在战斗中/收尾中 → 整个交给 battle
1. 分类(classify)  ┐ 并行
2. 准备(prepare)   ┘
3. 生成(generate)    按类别分派
4. 更新(update)      先出计划，再按计划落盘
5. is_battle → 战斗分支
```

分类五选一：**元对话 / 属性检定 / 游戏动作 / 角色互动 / 环境探索**。

生成有两条完全不同的路：

| 类别 | 方式 | Python 层的强制要求 |
|---|---|---|
| 属性检定 | 工具编排 | `narrate_opening`×1、`narrate_result`×1、**`calculation_step`≥1** |
| 游戏动作 | 工具编排 | 前两者各×1，`calculation_step` 可选 |
| 元对话 / 角色互动 / 环境探索 | 流式文本 | 无 |

### 2.1 靠代码保证、迁移后会失去的东西

迁移的风险清单，去向见 §3.2 与 §7：

1. 分类必须恰好一次工具调用、五选一、失败重试 3 次、`tool_choice="required"`
2. check 必须有计算步骤；opening/result 重复出现即判失败
3. `plan_panel_update` 必须调用一次，7 字段全必填
4. **`current_info.json` 由 Python 写**（`set_current_time` / `set_current_location`）——没有任何提示词负责它
5. 输出拼接格式由 Python 固定（`> formula` / `> 结果：xxx` / `dm_note` 前置 `> `）
6. 工具全失败时回退到纯文本 `content`
7. 元对话**不叠加** DM 注记，其余四类叠加
8. 战斗短路在全部提示词之前（按 §9.1.2 丢弃）

## 3. 新流程

**每回合四个阶段，全部由 skill 正文串联，代码不做编排。**

```
① 读     读本回合需要的信息（默认集 + 按需）
② 判类   五选一 → 读对应的生成 reference
③ 生成   按需调工具（roll_dice / search_rules）→ 全部结束后一次性输出正文 + 变更清单
④ 更新   把变更清单逐条落盘 + 对账
```

### 3.1 为什么这样改

| 旧 | 新 | 理由 |
|---|---|---|
| 分类与准备并行 | **读在前，判类在后** | 读到的内容能帮助判类；分类错的代价（走错分支、整段重来）远大于多等一次 |
| 取信息与生成切开 | **工具调用放进生成中间** | 符合游戏实际节奏（"要检定 → 投骰 → 暴击 → 再投 → 出结果"），也是 agent 的自然循环 |
| 生成分两条路 | **合并为一条：模型直接写正文** | 工具编排那条路存在的唯一理由是"Python 需要结构化片段来拼装正文"；模型直接写，拼装这一步消失 |
| 更新先出计划再派发 | **变更清单当待办，逐条落盘** | 见 §4.4 |
| Python 写 `current_info.json` | **由模型在 ④ 阶段写** | 旧设计里这层是 Python，迁移后会丢失（§2.1 第 4 条） |

### 3.2 丢弃的机制，与必须保留的语义

机械约束（调用次数、字段必填、拼接格式）大部分消失，因为它们服务的结构化片段不存在了。但语义要保留：

| 丢掉的机制 | 要保留的语义 |
|---|---|
| `calculation_step` 必须调用 | **属性检定必须展示计算过程与来源**（骰值 + 加值 + DC） |
| `narrate_opening` / `narrate_result` 各一次 | 正文结构：场景开场 → 结算 → 结果 |
| `narrate_result` 不得续写 | **检定只能写到成败，不得续写后果** |
| `plan_panel_update` 必填 7 字段 | 更新前的**清单枚举**（§4.4） |

> 把"机制"照搬进 skill 会让正文又长又死；把"语义"丢干净会让游戏跑偏。

### 3.3 骰子的信任模型必须改写

旧提示词写"检定用的骰子**由系统提供**，不得篡改"——那是因为旧系统里骰子由 Python 投出。新设计里**骰子由模型自己调 `roll_dice` 拿**，所以界线重写为：

> **你调用 `roll_dice` 拿到的值才是有效骰值；没有调用工具就不得在正文里出现具体数值。**

### 3.4 "等所有操作结束再输出"必须显式写

> **所有工具调用与计算都结束后，再一次性输出正文。**

模型中途吐出的叙述**不会分成两个气泡**（前端按回合累积，`done` 兜底收尾），但**半成品会留在最终正文里**，玩家会看到"话说到一半又重说"。

## 4. 上下文与状态策略

### 4.1 先分清三个不同的东西

| | 是什么 | 新鲜度 | 累积 |
|---|---|---|---|
| **① 磁盘存档** | `Account/<u>/Saves/<id>/data/*` | **永远是当前值**（唯一真副本） | — |
| **② 对话历史（转录）** | 每次 `read` 结果、每次 `write` 参数 | **当时那一刻的快照** | ✅ 只追加，会被压缩总结 |
| **③ 系统提示词** | 每个模型步骤重新组装、每次请求重发 | 每次组装求值 | ❌ 不进历史 |

- **`read` 不可能返回旧内容**——它读磁盘，永远是 ①。风险只有"模型**没读**，转而用了 ② 里那份旧的"。
- **"每回合重新组装"只作用于 ③，碰不到 ②。** ② 只追加，不会因组装而刷新。
- 把文件内容放进 ③ **需要写插件**（配置层只有 `model` / `cwd` 两个内置变量）。本项目决定不写。

### 4.2 读取策略：不注入，全部写在 skill 里

**不写系统提示词插件，也不用适配层注入面板内容。** 由 skill 正文要求模型每回合读。

| 项 | 做法 |
|---|---|
| **默认集** | 每回合读：`current_info.json`、当前地点文档、`characters/allies/*.md`、`plot/cur_main_plot.md` |
| **其他** | **按需读**：用到背包就读 `inventory.md`，移动就读 `world/map.json`，涉及状态就读 `status/*`。不确定就先读 |
| **代价（已接受）** | 每回合多一次模型往返；默认集合计约 1880 字符（约 1000–1300 token） |
| **代码层约束** | 无 |

> 曾考虑"适配层注入 `current_info.json`（96 字符）"与"写系统提示词插件做一份不累积的最新版本"，**都放弃**，改为 skill 约束。
> "不注入"的前提是模型得看得见有哪些文件——靠一个**只读工作区目录的小工具**补上，见 §9.3.1。

### 4.3 状态真源规则（写进 SKILL.md）

**不是"存档为准"**——那句是错的：存档更新遗漏时，它会**静默把已发生的事回滚**。

> **状态的真源是本局实际发生过的事，不是某个文件。**
>
> - **本回合叙述里明确改变了的项 → 以叙述为准**（例如本回合扣了 5 血）
> - **本回合没被改变、且来自本回合读取的项 → 以存档为准**
> - 叙述与存档冲突时：**以叙述为准，并且必须立刻把存档改对**（§4.5）
> - **没有在本回合读取过、也没有在本回合写入过的数值，不得引用**——历史里的旧快照一律不作数

必须同时写明，否则模型会误判：

> 不要把"**读到的位置更靠后**"当成"**它记载的状态更新**"。一次读取出现在转录后部，是**读的时间**晚，不代表它记载的**状态**晚。

### 4.4 变更清单（叙述的一部分，充当 update 待办）

模型在写正文的同一口气里，另起一小块机械信息声明本回合的数据变化：

```
（正文……）

> 面包：3 → 2
> HP：20 → 15
> 时间：下午 → 傍晚
```

格式沿用旧系统的呈现（旧系统本来就在正文里插 `> 12（当前HP）+ 4（恢复值）= 16`、`> 结果：HP增加4点`），所以不改变游戏风格。它一次解决三件事：

1. **对账有依据**——"面包 3→2"是明写的，不必从叙述里猜
2. **它就是 update 的待办清单**——替代被丢掉的 `plan_panel_update`：先枚举、再逐条执行、改完回清单核对
3. **可与 git diff 交叉核对**（可选，§4.6）

**约束**：只在数据确实发生变化时声明；没有变化就不写这一块。

### 4.5 对账（写进 update reference）

> 如果你发现存档与最近几回合的叙述不一致（例如叙述里扣了血、但存档 HP 没变），**必须在本回合把它改对**。

**触发条件是"清单说变了、面板没变"，不是"模型觉得不对"**——后半句防止模型凭印象覆盖一个本来正确的面板。

没有这条，漏一次更新就是**累积性错误**：面板永远落后一格，后面每回合都在错误状态上推进。有了它，"忘了更新"从累积错误变成**可自愈**。

### 4.6 git 的角色（收窄）

git 快照（P5-2）**不参与上下文新鲜度**——因为"模型看不到的改动"在当前结构下没有来源：模型自己的改动在对话历史里；`double_check` 要删掉（§2.2）；UI 改的是 `meta.json` / `settings.json`，不在 `data/` 里。

**git 只保留三个用途**：

1. **回退**（P5-2 已实现的 `rollback`）
2. **审计**（定位是哪一回合改坏的）
3. **展示**（"本回合改动了这些文件"，既是 UX 也是可审计性）

**提交点**：每回合 ④ 阶段结束后提交一次。`HEAD~1..HEAD` 即"上一回合的改动"。

## 5. skill 结构

```
Skills/game-zh/                ← 已建（SKILL.md 已写完，references 待写）
  SKILL.md                    流程四步 + 全局不变量
  references/
    read-panel.md             本回合读什么、默认集与按需清单（§4.2）
                              先用目录工具看有哪些文件，再决定读哪些（§9.3.1）
    classify.md               五个类别与判据
    gen-meta.md               元对话
    gen-check.md              属性检定（含"必须展示计算过程"）
    gen-action.md             游戏动作（含"本回合不是战斗推进回合"）
    gen-interaction.md        角色互动
    gen-exploration.md        环境探索
    narration-rules.md        **仅主线相关**：不抢进度 / 不失控发散 / 停滞轻推 / 以面板为准不得发明主线
    update.md                 变更清单 → 待办 → 对账（§4.4 / §4.5）
    update-inventory.md       背包 / 状态 / 人物（含 `current_info.json`）
    update-location.md        地点与地图
```

**结构决定**

- **DM 注记的切分**（与旧系统不同，是刻意的）：

| 内容 | 归哪 | 为什么 |
|---|---|---|
| 人称、篇幅、玩家输入默认是游戏内言行、"不得编造" | **SKILL.md（全局不变量）** | 这些对**所有**类别都成立，**包括元对话**。放进"非元对话才读"的 reference，元对话就丢了它们 |
| 主线骨架（不抢进度 / 不失控发散 / 停滞轻推）、以面板为准不得发明主线、隐藏剧情不启用 | `narration-rules.md`（非元对话才读） | 这些是**推进游戏**用的约束，元对话不需要（§9.1.7） |

  这样两边**不重复**，也避免同一句话写两处漂移。

- **DM 注记独立成 reference**：旧系统是"非元对话才叠加"，独立出来才能保留这个条件（§9.1.7）。
- **`read-panel.md` 独立**：内容是每个类别的共同前置，独立出来让 SKILL.md 保持短。

**实际目录结构（现状，平铺）**：

```
Skills/
  consult-zh/{SKILL.md, references/}
  consult-en/{SKILL.md, references/}
  game-zh/{SKILL.md, references/}
```

> 设计里曾写过"按流程分层"（`Skills/consult/`、`Skills/game/`），**那一层从未建立**，只是方案。

**这带来的后果（未解决）**：`customSkillDirs` 只认"根目录"，**没有排除某个 skill 的配置**。
平铺时无论把哪个根给它，两个 preset 都会看到全部三个 skill——§9.1.3.1 想要的"模型没有可弄混的候选"**失效**。

**本期决定：不动，保持平铺。** 隔离问题留到接线 preset 时再定。

三条出路（供那时选择）：

| 出路 | 说明 |
|---|---|
| (a) 加一层目录 + 拆两个 preset | 把"选 consult 还是 game"从**模型**挪到**适配层**（按 `save_id`）——不是消除选择，是让选择变成确定的代码判断 |
| (b) 适配层每回合显式调用 skill（如 `/game-zh`） | 若能做，**一次解决四件事**：①打开游戏自动加载 ②不会误选 ③不必加目录层 ④不必拆两个 preset（省掉两份 YAML 的漂移风险） |
| (c) 放弃隔离，靠 description 区分 | 即先前判定会**静默出错**的那条：游戏回合走了 consult 就不更新任何面板，还看不出来 |

> 为什么 (a) 有效：`customSkillDirs` 只认"根目录"、没有排除项，所以**只有让每个 preset 各自指向一个只含本流程变体的根**，
> 模型才真的看不到对方的 skill。平铺时做不到这一点。

#### (b) 已核实可行（推荐）

**harness 内置 `/名字` 注入，不需要插件。** 证据链：

| 环 | 事实 | 出处 |
|---|---|---|
| 1 | 支持 `/名字` 把 skill 指令注入当轮次 | `dsh-tool-skill` README：「**用户显式调用。** 直接用户输入中的 `/name` token 若指名某个用户可调用 skill，会把该 skill 的指令注入当轮次，而无需模型自行加载」 |
| 2 | 我们的 skill 默认**允许**被调用 | `dsh-skill-filesystem` README：省略 `user-invocable` 时**默认允许** |
| 3 | 监听器扫"已认领的用户消息"，挂在 `agent/pre-step` | 同 README「调用边界」 |
| 4 | 适配层发的就是普通用户消息 | `Relay/adapter.py:186` `session.prompt{text}` → `dsh2server/lib/bridge.js:97` → `lib/host.js:550-575` 构造 `{role:'user', content, source:{kind:'user'}}` → `agent.followup()` |
| 5 | `text` 由适配层构造 | 所以可以前置 `/game-zh ` |

**一次解决四件事**：①打开存档自动加载 ②不会误选 consult ③不必加目录层 ④不必拆两个 preset（省掉两份 YAML 的漂移风险与那个机械检查）。

**实现要点**：适配层发 `/game-zh <玩家输入>` 给 DSH，但 `persist` 只写 `<玩家输入>` 进 `chat.db` —— 玩家的历史记录不会被这个标记污染。

**⚠️ 一个未定死的细节**：注入的 skill 正文是**每回合重发**（不累积）还是**留在历史里**（累积）？官方两处措辞不一致（「追加在该**步骤**所有其他注入之后」vs「被接纳内容成为保留历史，或成为每次请求重复的会话前缀」），静态读不出来。

- **默认按"每回合都发"**：两种出错方向不对称——发多了只是费 token，发少了会让后续回合丢掉流程指令（行为错误）
- **实测确认方式**：跑完两个回合后看 session 日志里有没有出现**第二份** `<skill_content>`；若有，说明它在累积，改成只在首回合发

## 6. 迁移映射（旧文件只是素材，不是规格）

> **这是参考来源对照，不是逐份翻译的任务单。** 我们从零写新的 reference：旧提示词提供素材（约束、例子、措辞），但不决定结构、不决定措辞、不需要一一对应。旧文本自相矛盾或因旧编排机制而存在的内容一律不搬。
>
> 反过来，那些**因为踩过坑才写下的约束**（字数、不得编造、`oldText` 唯一、`map.json` 结构）要逐条判断是否保留——不要因为它们藏在某份文件里，就跟着那份文件一起丢。

| 旧文件 | 去向 |
|---|---|

#### 9.1.3.1 按流程各给一个 preset —— ⚠️ **已作废（见下）**

> **本节方案不再采用。** 现方案：**一个 preset + 适配层注入 skill token**（`/game-zh` / `/game-en`），
> `Skills/` 平铺。决定性的一条是：**"隔离"要解决的问题在注入方案下根本不成立**——
> game 选哪个 skill 是**系统按存档语言定的**（`server.game_skill_for`），
> 模型不需要在 game 与 consult 之间做选择，也就没有"选错流程"这个自由度。
> consult 不注入，它确实要在 `consult-zh` / `consult-en` 之间选，但那是**语言**（可观察事实），不是流程。
>
> 残余风险（诚实记下）：平铺目录里 consult 的 skill 对 game 会话**也可见**，模型理论上仍可能去加载它。
> 缓解是**每轮显式注入**——流程指令直接进上下文，不靠模型自己挑。实测（headless 真实回合）模型按
> `read-panel.md` → `classify.md` → `generation/exploration.md` 走完，没有被 consult 干扰。
> 若以后实测出现误选，本节的两 preset 方案仍是现成的退路。
>
> **补充理由**：consult 的定位是"游戏里碰到不确定就想问一句"的**短问答**，不是长篇讨论；
> 而且咨询本来既不需要读存档文件、也不需要投骰子——那两个工具放在它的工具面里也不会被调用。
> 为了一个不会发生的调用去多养一份 preset（以及它的漂移风险）不划算。
>
> 因此也不再需要下面那份"除 skill 根外完全相同"的机械检查。以下原文保留作背景。

入口已经决定流程（"咨询城主"面板 vs 存档），而入口在适配层是已知的（`save_id`：咨询恒为 `consult`）。适配层建会话时按 `save_id` 选 preset（`Relay/adapter.py:120` 已在调用 `agentPreset.select`）。

| preset | 挂载的 skill 根 | 模型看到的 skill |
|---|---|---|
| `letsplaydnd-consult` | `Skills/consult` | `consult-zh` **与** `consult-en` |
| `letsplaydnd-game` | `Skills/game` | **只有** `game-zh` |

**隔离的是「流程」，不是「语言」**——这个区分是本节的关键：

| 要隔离的 | 模型需要做的事 | 可靠性 |
|---|---|---|
| **流程**（consult / game） | 判断用户的**意图**（在问规则还是在玩） | ❌ 真的会错，且后果静默：游戏回合走了 consult 就**不更新任何面板**，玩家看着正常、存档却停住了 |
| **语言**（zh / en） | 观察用户输入**本身是什么语言** | ✅ **可观察的事实**，不是意图推断 |

所以：**流程之间隔离，流程内部的语言变体共存。**

**为什么必须用 preset**：一个 DSH 实例同时服务两种流程（一用户一实例，会话按 `save_id` 分），所以

- **环境变量**不行——进程级，两流程共用同一进程
- **按会话传 skill 目录**不行——`customSkillDirs` 是装配期配置，没有按会话入参
- `preset` 恰好是**唯一按会话选择**的装配单位（组装在 agent 生命周期内只装一次，选不同 preset 只影响该会话）

**代价与兜底**：preset **不支持继承**，`@cordisjs/plugin-include` 也没随 dsh 打包，所以两个 preset 是两份近 100 行的 YAML、只差 `customSkillDirs` 一行 → **漂移风险**。兜底：**加一个机械检查**，断言两份文件除 skill 根那一行外完全相同，把"改了 A 忘了改 B"变成吵闹失败。

> 若以后要单一真源：抽 `insert:` 片段文件，或写脚本从模板生成两份。当前两个文件 + 一个检查够了。

#### 9.1.4.1 地点更新 reference 由两稿合并新写

`4.2 update_location.md` 与 `4.3 update_new.md` 是同一件事的**两稿**：4.3 是 4.2 的超集，多了「更新旧地点」整节（人物常驻判定、物品表格、事件记录）。

#### 9.1.6.1 `current_info.json` 由模型直接改写

**决定**：④ 阶段由模型直接写，**可以整体重写**，不必逐字段。

#### 9.1.7.1 元对话不叠加 DM 注记

### 9.2 语言策略（已裁决）

先把两件独立的事分开：

| | 是什么 | 状态 |
|---|---|---|
| **A. `search_rules` 的 `language` 参数** | 每次检索调用要显式给出语言 | 已实现（`Literal` + enum + 必填），见 `spec.md` P2「双语化」 |
| **B. 语言怎么选** | 谁决定这一轮用 zh 还是 en | 见 §9.2.2 |

#### 9.2.1 A：保留，且保持必填

- MCP 服务**跨会话共享且无状态**，无从知道调用来自哪个会话 → **必须**由调用方给出
- 必填是刻意的：漏传会报错；给默认值会**静默查错库**（`RAG._normalize_lang` 对任何不以 `en` 开头的值一律退回中文库）
- 已实测非法值被拒，且错误信息带合法取值

**A 与 B 的选择无关，无论 B 走哪条，A 都要保留。**

#### 9.2.2 B：结论

| 项 | 决定 |
|---|---|
| **consult** | **维持按用户当前输入语言选 skill 变体**。两个语言变体都可见 |
| **game** | **开局确定且不可更改**。理由很硬：已有存档文件是原语言的，**全翻译不可能** |
| **语言切换** | 本期不处理 |

> **成本确认**：`tool-skill` 的目录是**首次请求前注入的一条持久消息**（不是每步重发的系统提示词），且只在目录变化时追加完整替换。所以多几个语言变体只是那条消息里多几十 token，**一次性**。

**备选（留待以后）**：若实测发现按输入判语言会出错（中英混杂、只有专有名词），可加"界面设置给默认、输入给覆盖"两层。consult 的语言其实也已由界面设置确定且可改，换成"按设置钉"同样可行。

#### 9.2.3 语言是怎么确定的（已核实）

**有三个不同的东西**：

| | 是什么 | 来源 | 可变 |
|---|---|---|---|
| `Account/<用户>/settings.json` 的 `language` | **界面语言**（UI 显示） | 设置里的语言开关 | ✅ 随时 |
| `consult` 那条 meta 的 `in_game_language` | **咨询内容语言**（咨询没有存档内容，所以跟随界面） | 由界面语言**镜像**过来 | ✅ 随时 |
| `game_*` 存档 meta 的 `in_game_language` | **游戏内容语言** | **模板**，创建时拷入 | ❌ **创建后不可改** |

> **界面语言与游戏内容语言是两件事。** UI 设成英文、玩中文存档是完全正常的状态——游戏输出仍是中文。**读语言时不能读错来源。**

**游戏的完整链路**

### 9.3 目录可见性（已裁决）

#### 9.3.1 加一个只读工作区目录的工具

**问题**：旧系统每回合注入 `data/` 的目录树（343 字符），这是"不确定就先读"能成立的前提。新设计不注入任何东西，而极简模式的 `read` **只读普通文件、给目录返回 `FS_NOT_REGULAR_FILE`**，模型因此**列不出目录**——读得到固定路径，读不到**名字可变**的文件（有哪些地点文档、有哪些盟友）。

**已核实的事实**：工具面只有 `read` / `read_image` / `write` / `edit`；后端 `fs-local` **有** `listDir`，但 `dsh-tool-fs` 刻意不暴露给模型（官方原话："未交付面向模型的目录列表工具……`dsh-tool-fs-search` 包则提供基于 ripgrep 的 `glob` 与 `grep`"）。当前 preset 没挂它。

**决定（已修正）**：加一个只读工作区目录的工具 `list_dir`，实现成**进程内的 DSH 插件**
（`dsh/plugins/tool-list-dir/`，插件名 `dsh-tool-list-dir`），挂在 preset 里。
**根不由模型给**：模型只传相对路径 `path`，工作目录由插件从 `exec.agent.session.header.cwd` 取。
已实现、已单测（15 条）、已装进 profile。

| 项 | 结论 |
|---|---|
| 形态 | **DSH 插件**（`ctx.tools.register` 一个裸 `ToolDefinition`）。理由见下 |
| 签名 | `list_dir(path=".")`——**只有一个相对路径参数**，根由系统给 |
| 范围 | **上界是会话工作目录**（游戏流程里就是 `<存档>/data`）。`..` 出不去，也看不到存档文件夹、别的存档、账号目录 |
| 为什么上界是工作目录 | 与 P5-1 的读白名单**同一个圈**：能读的就能列，能列的就能读。consult 的 cwd 是 `Saves/consult/data`，同样自洽 |
| 包含性检查 | 两道，**都过才放行**：词法（`displayPath` 在 cwd 内，挡 `..` 上溯）+ 真实（`targetKey` = realpath 在 `realpath(cwd)` 内，挡工作目录里已存在的符号链接） |
| 读内容 | **不读**。`ctx.fs.listDir()` 只 stat（官方注释 `file contents are never read`），所以围栏即便有洞，泄露面也只有文件名 |
| 深度 | 一层；模型逐层下探。**不注入**，符合 §4.2 |
| 排序与上限 | 目录在前、文件在后，各自按名字排序；跳过点开头的项；默认最多 200 条（`maxEntries` 可配） |
| 失败关闭 | 拿不到会话 cwd → 拒绝。与 fs-readguard 同一取舍 |
| 错误怎么报 | 抛 `Error` 即可：进程内工具的 `toolErrorResult` 会把消息原文包成 `Error: <消息>` 交给模型（不需要 MCP 那边的 `ToolError`） |

**为什么改掉 MCP 那版**：MCP 服务只收到自己 schema 里声明的参数，**拿不到会话上下文**
（唯一额外通道是那一行的静态 `headers`）。所以它只能是 `list_dir(base, path)`——让模型自己报工作目录，
**模型报什么就信什么**。上界收在存档根也只能靠"base 必须在 `Account/` 之内"兜，
实测能拿**另一个存档**的 `data` 当 base 列出它的地点文件名（见下"已实测的残留"）。
进程内注册没有这层限制，`exec.agent.session.header.cwd` 就是天然正确的根。

**为什么 `link:` 插件这条路现在走得通**（原判断"走不通"已作废）：
`link:` 装的插件 import 不到 `@deepseek-ai/*`（实测 `ERR_MODULE_NOT_FOUND`）**只意味着不能用 `defineTool`**，
而 `ctx.tools.register()` 收的本来就是**裸 `ToolDefinition`**：
`{ name, description, parameters, output: {schema, render}, execute }`
（`defineTool` 只是"入参 spec → JSON Schema + 校验"的包装；官方 `dsh-mcp-client` 自己就是手写的）。
代价只有一条：**入参校验要自己写**。本工具只有一个可选字符串参数，用 `typeof` 判即可。

**已实测的残留（旧 MCP 版，已随删除消失）**：`list_dir(base=<别的存档>/data, path="world")` 通过，
返回那个存档的地点文件名；内容仍读不到（`read` 受 P5-1 白名单拦）。
`base` 是模型给的，这就是根因。插件版没有这个残留——根不由模型给。**§10.5 的每用户凭证隔离仍是独立问题**。

**验收证据（真实 headless 会话）**：模型在一个回合里连续调用 `list_dir` 6 次，参数分别是
`{"path":"."}` / `world` / `characters` / `plot` / `characters/allies` / `status`，全部成功。
输出形如：

```
world/
  map.json
  渔村外围.md
  渔村杂货铺.md
  渔村村口.md
```

相对路径、目录在前、点开头项不显示，且返回的路径随即被 `read` 直接使用。
拒绝路径（`..` 上溯、绝对路径、工作目录内的符号链接、拿不到会话 cwd）由单测覆盖，15/15 通过。
解会话日志看真实工具调用的脚本：`poc/dump-session.mjs`（会话日志是 concatenated zstd frames，
`zstdDecompressSync` 只解第一帧、其余静默丢弃——这个坑也踩过）。

#### 9.3.2 为什么不挂 `dsh-tool-fs-search`

`glob` / `grep` 是**通用文件系统搜索**（ripgrep 直接吃路径，输出是路径与匹配行），本身**不受读白名单约束**——挂上就必须扩守卫，否则模型能 `grep -r` 扫整个文件系统，**绕过 P5-1**。而专用工具把范围内建，**更窄也更安全**。我们只需要"看得见有哪些文件"，不需要内容检索（读文件有 `read`）。

#### 9.3.3 为什么不引入代码执行（PTC / `run_code`）——已考察，否决

官方原文（`dsh-code-runtime-worker-thread` README）：

> **应将执行的代码视为与 bash 拥有同等权限**：本包限制环境暴露和资源使用，但**不将代码与宿主隔离**。
> 程序运行时的权限与 bash 工具相当：**它可以访问 Node API**。

所以代码执行只有一半受管：

| 通道 | 受 `fs-readguard` 管辖吗 |
|---|---|
| 代码里通过 SDK 调用工具（`tools.read(...)`） | ✅ 受——SDK 绑定调用**重新进入完整工具流水线** |
| 代码里直接用 Node API（`fs.readFileSync('/…/.env')`） | ❌ **不受**，完全绕过工具层 |

**引入 PTC 就等于拆除 P5-1 的读白名单**——正是不变量里写的"等价物"。它的两个好处（列目录、一次程序批量读完而省一次往返）真实，但**前提是安全边界换成内核级隔离**（容器 / 微虚拟机 / bwrap / systemd 命名空间）。

> 真要上 PTC，应与"把实例启动方式改成 systemd/容器"**一起做**——systemd 命名空间在"手工起实例"的现状下不生效，这个前提得先解决。**不属于 P6。**

| **机械约束消失** | 旧系统的"必须调用 N 次"没有替代强制 | 靠 skill 语义约束；实测不稳再考虑挂回 `todo_write`（见下） |
