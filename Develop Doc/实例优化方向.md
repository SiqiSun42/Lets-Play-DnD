# 每用户实例：冷启动与内存的优化方向

> 记录**还没做**的优化。现状：实例按需拉起、**永不自动回收**，冷启动由用户第一条消息承担。
> 相关实现：`Relay/instances.py`；触发点：`server.ensure_user_instance()`。

## 先分清两层（问过的问题）

| 层 | 粒度 | 由谁决定 |
|---|---|---|
| DSH 进程 + `DSH_HOME` | **每个用户一个** | 结构性：DSH 的凭据是 DSH_HOME 级的，key 只能这么隔离 |
| DSH 会话 | **每个存档一个**（consult 也算一个"存档"） | `DshSessionMap`：`(用户名, 存档 id) → session`，`cwd` = 该存档的 `data/` |

所以：**N 个用户 = N 个常驻进程**；同一用户在多个存档间切换**不会**再拉起新进程，只是新会话。

## 冷启动是什么时候、花在哪

- **什么时候**：某用户的实例不在线时，他发的第一条消息会触发 `ensure()`：铺 `DSH_HOME` → 写凭据与 patch → 登记中转 key → 起 `dsh web --port 0` → 等上线。
- **花在哪**（按量级）：Node 进程启动 + 组装插件树（要 import 上百个模块）+ 首次 agent 组装 → 连上中转 → 最后才是模型请求。
- **实测**：本机（M 系 Mac）从 `ensure()` 到上线 **7.6 秒**；服务器（891 MiB + swap）预计 15~40 秒，**待实测**。

**什么时候会"再冷启动一次"**：

| 情况 | 说明 |
|---|---|
| 机器重启 / 实例被 OOM 杀掉 | 实例没了，下次消息重拉 |
| 显式 `stop()` | 目前只有管理侧能触发（还没有空闲回收） |
| **Flask 重启** | 实例**不会死**（它是独立进程组），会自己重连中转；但重连有退避（最长 60 秒），所以重启后每个用户的第一条消息可能撞上等待窗口（`wait_for_instance` 等 45 秒）。consult 旧路径也有同样的毛病 |

## 优化方向（按性价比排）

### 0. 思考档位按 provider 补齐 —— 只做了 deepseek

跑团回合用 `low` 足够，`high` 是杀鸡用牛刀。现状（`Relay/instances.py`）：

| provider | 走哪条路 | 思考档位 |
|---|---|---|
| **deepseek** | 内置适配器 `llm-deepseek`（provider `deepseek-official`，端点由 `DEEPSEEK_BASE_URL` 传） | ✅ `reasoningEffort: low`（实测：请求走到鉴权，不再报档位错误） |
| 其它（qwen / openai / groq / kimi） | 手写的 pi-ai OpenAI 兼容路由 | ❌ **不设**——模型条目没声明 `reasoningEfforts`，DSH 会拒绝任何档位（实测 `UNSUPPORTED_REASONING_EFFORT`） |

补齐的办法：在手写路由的模型条目上声明档位与**发给端点的字面值**：

```yaml
models:
  - id: qwen3.7-plus
    reasoningEfforts:
      low: low        # 值是"dispatch 发到线上的拼写"，各 provider 可能不同
      high: high
```

⚠️ 各家字段不一样（OpenAI 系是 `reasoning_effort`；DashScope/Qwen 系是 `enable_thinking` / `thinking_budget`；
自建端点可用 `thinkingTokenBudgetField`），**猜错会让每一回合都在请求构造阶段失败**。
所以要先查该 provider 的协议再声明，并逐家实测（假 key 下若报 AUTH 就说明档位被接受）。

另外这个档位**也该给用户自己调**：落点就是 `Account/<用户名>/settings.json`（现在是写死的默认 `low`）。

### 1. 空闲回收 —— 这台机器上最先该做的

891 MiB 内存下，**常驻进程数**才是真瓶颈（不是速度）。按"最后活动时间"超过 N 分钟就 `stop()`。

- `stop()` 已经实现（SIGTERM 进程组 + 撤销该用户的中转 key），下次 `ensure()` 会重新登记 ✓
- 需要一个"最后活动时间"的来源：适配层每次下发提示词时记一下（内存 dict 即可，不需要持久化——重启后本来就都得重拉）
- 权衡：回收得越积极，冷启动越频繁 → 所以要和第 2 条一起做

### 2. 预热 —— 把冷启动藏进"用户还在看界面"的时间

`ensure_user_instance(username)` 本身就**幂等**（在线就直接返回），所以只要换个时机提前调它。可选触发点，按效果排：

| 触发点 | 效果 | 代价 |
|---|---|---|
| **打开存档时**（前端已经在打 `/api/game/messages`） | 最好——用户马上要说话，提前几秒到几十秒开始起 | 打开存档但没说话的用户也占一个进程 |
| **登录/注册成功时** | 更早，用户还在看界面时就好了 | 建了号不玩的人占进程（要靠第 1 条回收） |
| 收到消息时 | 现状（等于没预热） | — |

两种都做也不冲突：登录预热一次，打开存档时若已被回收就再预热一次。

⚠️ 预热**要求该用户已经配了模型 key**，否则会失败（失败只记日志，不抛给用户；他发消息时还会再试一次 ✓）。

### 3. 让等待可见

现状是前端**静默卡住几十秒**，用户不知道在等什么。两个便宜做法：

- 适配层在起实例期间先发一条 SSE（例如 `{"type":"thinking","delta":"（正在准备 DM，首次约 30 秒）"}` 或一个独立事件）
- 或前端在 `sendChatBusy` 期间把占位提示换成这句话

改动都很小，但体感差别最大。

### 4. Flask 重启后的重连窗口

实例会自己重连，但退避最长 60 秒。可以在收到请求时"主动催一次"——本质上就是第 2 条：`ensure()` 会等它上线并把上线时间压到实际重连时间。

### 5. 缩短启动本身（最后一公里）

先量清楚那 10~40 秒的构成（Node 冷启动 / 插件树 import / profile 组合 / 首次模型请求分别占多少），再决定：

- Node 22+ 有 `module.enableCompileCache()`：把模块编译结果缓存下来，能显著缩短 "import 上百个模块" 那段。DSH 有没有用到、有没有开关，待查
- 插件树精简：MCP 客户端等能不能延迟挂载（但要小心：工具面是装配期定的）
- 用 `dsh --profile … --dump-config` 之类只组合不启动的路径测"组合"耗时，与真实启动对比

### 6. 明确**不**采用的

| 想法 | 为什么不行 |
|---|---|
| 多个用户共用一个实例 | 凭据是 DSH_HOME 级的 → 等于回到"所有人烧操作者 key"的老问题（§10.5） |
| 多用户共用一个 `DSH_HOME` | 同上；而且会话/存档状态也会互相看得见 |
| 用后即停（每条消息都重启） | 每条消息都付一次冷启动，比常驻更糟 |

## 度量方式（改之前先量，别拍脑袋）

| 想看什么 | 怎么看 |
|---|---|
| 冷启动总耗时 | `app.log` 里 `ensure` 前后的时间戳（可以临时加一行日志）；或 `instance.log` 的第一行时间 vs `bridge/connected` |
| 单实例常驻内存 | `ps -o pid,rss,cmd -p $(pgrep -f "profile letsplaydnd" | head -1)` |
| 回收是否有效 | 回收后 `free -h` 的 available，以及进程数 |
| 预热命中率 | 记一下"发消息时实例已在线"的比例（一行日志即可） |
